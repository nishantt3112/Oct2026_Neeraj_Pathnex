			- so this was a scenrio created in the lab where a node was made unhealthy intentionaly by rebooting it then all the pods which were evicted 
			- so how pods are actually evited in real productions during a node maintenance or in a controlled way volunterarily 
			- so first we have to do kubectl get nodes 
			- kubectl cordon nodeip 
			- this means we are  marking the node as unschedulable and no new pods will be scheduled by the scheduler.
			- then kubectl drain node 
			- this means we want the pods to be terminated or evicted gracefully 
			- here gracefully means all the ongoing process or the pods which are currently service will complete their tasks and then after those pods will be terminated so that users will not face sudden app crash.
			- then after updating the node 
			- again we will run the kubectl uncordon 
			- this means now we are marking the node as schedualable and the after getting the status of node as Ready all the pods or workload will be scheduled 
			- so there comes a PDB which stands for pod distruption budget which means it is a controller which make sures that during any controlled pod eviction process a min number of pods should be up and running if the minAvailable condition is crossed then it will stop the pod eviction process this is used so that at any point of time during pod eviction the application should be up and running without a downtime so lets say there are 10 pods of an app and in PDB we defined minAvailable: 2 then 2 pods will be running all the time so that app could serve the traffic.
			- these are basically used in maintenance or cluster upgrades OS updates patchign etc simply in controlled scenarios not in uncontrolled scenarios like node failure az failure network disconnections etc.
			- and labels and selectors are used to discover the pods by the PDB
		- affinity - low latency 
			- affinity means affection and if we want that a specific pods or workload should run on a specific node then we can use nodeaffinity rules so there are conditions like hard condition requiredDuringSchedulingIgnoredDuringExecution this means labels and selector will be matched during schd and if a it does not match it wont be schd and later after pod deployment if labels are changed then the pods will not be evicted .
			- IgnoredduringScheduling means this is soft condition so if the labels and selectors doesn't match and there other scheduling conditions gets fullfilled then pod will be placed.
			- node antiaffinity -- this means if we dont want to place a specific pods on a specific nodes then we can add this nodeantiaffinity rules 
			- so by using podaffinity rule we can achieve low latency because two pods will be always placed with each other.
			- and there is a topology key like kubernetes.io/topology=az or node this means pods will be distributed accross the nodes OR Azs to achieve high availabilty on node level and on AZ level
